# Data Dictionary: Raw Layer

> **All data described here is synthetic.** It is generated by
> `python -m riskplatform.ingestion.generate` from `config/generator.yaml`. Its shape follows
> the data contract in `src/riskplatform/schemas.py`. No figure describes a real bank.

The raw layer is written to `data/raw/` (ignored by Git) and has two tables:

| Table | Files | Grain (one row per...) | Rows with default config |
|---|---|---|---|
| Positions | `data/raw/positions/date=YYYY-MM-DD.parquet` (one file per business day) | position per date | 54,000 (900 positions x 60 days) |
| Market rates | `data/raw/rates.parquet` | date, currency and tenor | 1,440 (60 days x 3 currencies x 8 tenors) |

The contract is enforced on generation: `generate()` validates both tables against
`positions_schema` and `rates_schema` before anything is written. Both schemas are `strict`
(no extra columns allowed) and `coerce` (values are converted to the declared type).

---

## 1. Positions

One row per banking-book position per business day.

### Columns

| Column | Type | Allowed values / rule | Meaning |
|---|---|---|---|
| `date` | datetime | business day (Mon-Fri) | Reporting date the row describes. |
| `position_id` | string | unique per `date` | Stable ID of the position. It keeps the same ID every day. Format: `<entity>_<currency>_<category>_<NNN>`, e.g. `BANK_UK_GBP_central_bank_reserves_001`. |
| `entity` | string | `entities[].name` in config: `BANK_UK`, `BANK_EU`, `BANK_US` | Legal entity that books the position. |
| `currency` | string | `currencies` in config: `GBP`, `USD`, `EUR` | Currency the position is denominated in. |
| `category` | string | `categories[].name` in config (13 product types, listed below) | Product type. Drives the side, rate type and maturity range. |
| `side` | string | `asset`, `liability`, `off_balance_sheet`; must equal the category's `side` in config | Where the position sits on the balance sheet. |
| `balance_mn` | float | > 0 | Outstanding amount in **millions of the position's own currency** (no FX conversion). For `off_balance_sheet` rows this is the undrawn committed amount. |
| `rate_type` | string | `fixed`, `floating` | Whether the interest rate is fixed to maturity or resets periodically. |
| `interest_rate` | float | between -0.05 and 0.25 | Annual contractual rate as a decimal (`0.045` = 4.5%). |
| `residual_days` | integer | >= 1 | Calendar days until the position matures (residual contractual maturity). |
| `reprice_days` | integer | >= 1 and <= `residual_days` | Days until the interest rate next resets. Fixed-rate: always equal to `residual_days`. Floating-rate: next reset on its cycle, capped at maturity. |

### Table-level rules (from `positions_schema`)

1. `(date, position_id)` is unique.
2. `reprice_days <= residual_days`: a rate cannot reset after the position has matured.
3. Fixed-rate positions reprice at maturity: `reprice_days == residual_days`.
4. `side` matches the category's side in config.

### Product categories

| `category` | `side` | `rate_type` | Maturity range at issue (days) |
|---|---|---|---|
| `central_bank_reserves` | asset | floating | 1 |
| `govt_bonds` | asset | fixed | 90 - 3,650 |
| `covered_bonds` | asset | fixed | 180 - 2,500 |
| `corporate_bonds` | asset | fixed | 180 - 2,500 |
| `corporate_loans` | asset | floating | 30 - 1,800 |
| `retail_mortgages` | asset | fixed | 365 - 9,000 |
| `retail_stable_deposits` | liability | floating | 1 |
| `retail_less_stable_deposits` | liability | floating | 1 |
| `wholesale_operational` | liability | floating | 1 - 30 |
| `wholesale_non_operational` | liability | floating | 1 - 180 |
| `financial_institution_deposits` | liability | floating | 1 - 90 |
| `term_debt` | liability | fixed | 365 - 3,650 |
| `undrawn_committed_lines` | off_balance_sheet | floating | 365 - 1,825 |

The source of truth is `config/generator.yaml`. This table copies it for reading convenience.

### How the data is generated (summary)

- **Book:** every entity x currency x category combination has at least one position. The
  entity's home currency gets the full position count from config. The other currencies get
  `foreign_currency_weight` (20%) of it, with at least one position. That gives 300 positions
  per entity and 900 in total.
- **Balance sheet:** on the first day, asset balances are scaled so that, for every entity and
  currency, assets = liabilities / (1 - `equity_ratio`). Equity (6% of assets) is the gap; it is
  **not** a row in the table. Off-balance-sheet rows are excluded from this identity.
- **Daily balances:** each position takes an independent small random step every day
  (`daily_balance_drift`, `daily_balance_vol`). The identity therefore holds exactly on day one
  only.
- **Maturity:** `residual_days` counts down by one per row. When a position matures, it is
  replaced by an identical one at full original tenor (rollover).
- **Repricing:** floating-rate positions reset on a fixed cycle of 1-90 days
  (`floating_reprice_days`), with a random starting point.

### Planned use in metrics

| Column | Used for (planned, Phases 4-5) |
|---|---|
| `category`, `side` | Mapping to LCR/NSFR classes via **config** in Phase 4 (deliberately no `lcr_class` column). |
| `balance_mn` | Amount for every metric. |
| `residual_days` | LCR 30-day window; NSFR maturity buckets; IRRBB cash-flow timing. |
| `reprice_days`, `rate_type` | IRRBB repricing time buckets. |
| `interest_rate` | IRRBB earnings (NII) sensitivity. |
| `entity`, `currency` | Reporting splits: LCR is also monitored by significant currency. |

## 2. Market rates

One row per business day, currency and curve tenor.

### Columns

| Column | Type | Allowed values / rule | Meaning |
|---|---|---|---|
| `date` | datetime | business day (Mon-Fri), same dates as positions | Date of the curve. |
| `currency` | string | `currencies` in config | Currency of the yield curve. |
| `tenor_years` | float | > 0; `rates.tenors_years` in config: 0.0833 (1M), 0.25, 0.5, 1, 2, 5, 10, 30 | Point on the curve, in years. |
| `rate` | float | between -0.05 and 0.25 | Annual yield at that tenor, as a decimal. |

### Table-level rules (from `rates_schema`)

1. `(date, currency, tenor_years)` is unique.

### How the data is generated (summary)

- Each curve starts from a smooth shape: `short_rate + (long_rate - short_rate) * (1 - exp(-tenor / curve_decay_years))`.
  The short and long rates are set per currency in config.
- Every day the whole curve moves by one random shift (`daily_vol`); there is one random walk per
  currency.

### Planned use in metrics

IRRBB discounting and rate-shock scenarios (Phase 5).

## Known simplifications and limitations

These are deliberate or known gaps in the synthetic data. Each one is labelled so it is never
mistaken for a regulatory or market feature.

1. **Business days are Monday-Friday only.** There is no holiday calendar.
2. **Balances are in local currency.** There is no FX conversion. Cross-currency totals need an
   FX rate, which is not yet part of the raw layer.
3. **Parallel curve moves only.** Real curves also steepen, flatten and twist.
4. **`interest_rate` is fixed per position for the whole history.** It does not change when
   `reprice_days` reaches a reset or when a position rolls over. It is also drawn from one
   distribution (`interest_rate_mean` 4%, `interest_rate_sd` 1%) for every currency and side,
   so it is not linked to the market curves. For example, EUR positions average about 4% while
   the EUR curve is 2-3%. Phase 5 (IRRBB) needs this fixed in the generator.
5. **Non-maturity deposits are modelled as overnight** (`residual_days` = 1). Real banks apply
   behavioural assumptions to these for IRRBB. Those assumptions will be config in Phase 5.
6. **Rollover reissues an identical position.** The balance path, rate and tenor all continue
   unchanged.
7. **Equity is implied, not stored** (see "Balance sheet" above).
